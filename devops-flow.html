Todo DevOps Lab

How DevOps tools work together — end to end

From the first line of code to keeping the app healthy in production. Tools are grouped by job. One flow. Same todo app the whole way.

1. Tool groups by job

Same categories companies use. We add one group at a time on the todo app.

A · Write & collaborate

Change code without chaos

  • Editor / IDE
  • Git
  • GitHub · PRs, reviews

B · Build & package

Same app on every machine

  • Dockerfile
  • Image registry · GHCR / ECR
  • docker compose

C · Verify (CI)

Catch breaks before merge

  • GitHub Actions
  • pytest / linters
  • Scanners · Trivy / Dependabot

D · Configure & secrets

Env-specific, not in git

  • .env (local only)
  • GitHub Secrets
  • Vault / cloud secrets

E · Run & data

Process + durable state

  • Uvicorn / containers
  • SQLite → Postgres
  • Redis / S3 · later

F · Ship (CD / cloud)

Get a public URL

  • Railway / Render / Fly
  • AWS / GCP / Azure
  • Argo CD / Flux · later

G · Observe & operate

Know when it breaks

  • Logs
  • Metrics / alerts
  • Traces / runbooks

H · Scale (later)

Many instances, many teams

  • Kubernetes + Helm
  • Terraform / Pulumi
  • Load balancers

3. Same story as a timeline what happens when

0
You are here

Write the app locally

FastAPI + Jinja + SQLite on :8090. Client = browser, server = Uvicorn. No Docker/CI/cloud yet — on purpose.

1
A · Write & collaborate

Branch → commit → pull request

You change code on a branch. Git stores history. GitHub PR lets someone (or future-you) review before main changes.

2
C · Verify

CI runs on the PR

GitHub Actions starts when you open/push a PR. It installs deps, runs pytest (later lint + image scan). Red check = do not merge.

3
B · Package

Docker image

Dockerfile = recipe. Build produces an image (app + Python + deps). Same image runs on your laptop and in the cloud. Compose starts multiple containers with one command.

4
D · Config

Env vars & secrets

Port, DB URL, API keys differ for local / staging / prod. They live in the host’s secret store — never committed to Git.

5
F · Ship

Deploy to the cloud

Platform pulls the image (or buildpack), injects secrets, exposes HTTPS URL. /health proves the process is up. CD later means: merge to main → deploy automatically.

6
E · Run & data

App + database in production

App containers serve traffic. SQLite is fine for the lab start; Postgres becomes the shared source of truth when you need a real DB server. Redis/S3 appear when cache or big files hurt.

7
G · Observe

Logs, metrics, alerts

Something fails at 2am → logs show the error, metrics show the spike, alert pages a human, runbook says how to recover. Loop back to code (fix) or config (rollback).

8
H · Scale — later

K8s, Terraform, many regions

Only when one box is not enough: orchestrate many containers (Kubernetes), define infra as code (Terraform), add load balancers. Same flow — more automation underneath.

4. How tools talk to each other

Each arrow is a handoff. DevOps is mostly these handoffs.

From To What moves
IDE Git File diffs → commit
Git GitHub Push branch / open PR
GitHub Actions Webhook: “PR updated”
Actions pytest / scanners Checkout code, run commands
Actions Docker / registry Build & push image (when CI passes)
Secrets store Deploy platform Env vars injected at runtime
Deploy platform App + DB Start containers, attach volume/DB
App Logs / metrics stdout events + numeric series
Alerts Human + Git Page → fix → new PR (loop)
